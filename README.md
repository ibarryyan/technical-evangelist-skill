# Technical Evangelist · 技术布道者

一个把**复杂技术**转化为**可理解、可信、可采纳**的技术内容的 skill。

它不是"帮你写点东西"的写作助手。它约束三件事：**说得对**（准确性与证据分级）、**说得懂**（按受众校准深度与措辞）、**说得动**（推动采纳，而不只是介绍）。

适用于：技术文章与博客、技术演讲与 PPT、教程与开发者教育、架构解读、技术选型对比、社媒/社区内容、技术内容评审、选题挖掘。

---

## 一、它有哪些能力

### 1. 内容生产（7 类产出形态）

| 能力 | 产出物 | 关键约束 |
|---|---|---|
| **技术文章 / 博客** | 可直接发布的完整草稿 + 3 个候选标题 | 4–7 个主章节；开头必须是问题而非定义；结尾不给"总结的总结" |
| **技术演讲设计** | 演讲定位、核心论点、故事线、分段与时长分配、Demo 方案、Q&A 预案 | 必须按 85% 时长规划；开场 5 分钟必须回答"为什么要在意 / 解决什么问题 / 听完能做什么" |
| **幻灯片结构** | 逐页结构：标题（必须是论点句）、核心信息、素材类型、配图说明 | 一页一个信息；标题写名词短语即视为未完成 |
| **教程 / 开发者教育** | 有序可运行步骤 + 每步预期输出 + 失败排查 | 前 1/5 篇幅内必须出第一个可用结果；前置依赖须精确到版本 |
| **技术对比 / 选型** | 决策框定、维度表、分场景结论、采纳总成本 | 禁止宣布"普遍赢家"；必须写出"你偏好的一方在什么场景下会输" |
| **社交 / 短内容** | Thread、短贴、发布公告、Release Notes | 每条只讲一个观点；每条必须能独立成立 |
| **技术选题挖掘** | 选题、受众、痛点、核心洞察、差异化角度、建议形态 | 必须能压缩成一句话论点，否则视为未想清楚 |

### 2. 内容评审

6 维度 30 分制评分：技术准确性 / 逻辑结构 / 受众契合 / 记忆度 / 工程价值 / 语体。

- 每个维度有 1–5 分的行为锚点描述，不是模糊印象
- **准确性或逻辑任一项得 1 分 → 直接禁止发布**，总分再高也不抵
- 附 12 项缺陷速查表（论点孤儿、定义式开头、形容词空转、装饰性架构图、结论循环……），用于"感觉不对但说不清哪不对"的场景

### 3. 跨能力的底层机制

这三项是这个 skill 区别于普通写作提示词的核心：

**① 证据分级标签**

所有实质论断必须打标：`[FACT]` 可验证有出处 · `[INFERENCE]` 由已引用事实推导 · `[OPINION]` 作者判断 · `[UNVERIFIED]` 合理但未核实。

作用：杜绝把推测写成事实——这是 AI 辅助技术写作最常见的翻车点。

**② 采纳阶梯**

把读者分成 6 级：知晓 → 理解 → 评估 → 首次使用 → 常规使用 → 布道者。

诊断读者在哪一级，再决定产出什么。**绝大多数失败的"技术布道"，都是给第 3 级（正在评估）的人讲第 2 级（扫盲）的内容。**

配套：定位声明模板、异议处理表（6 类常见异议的真实问法 + 应对方式）、时间到首次价值（Time to First Value）设计。

**③ 受众校准**

8 类受众（初学者 / 开发者 / 资深开发者 / AI 工程师 / 架构师 / 技术负责人 / CTO·EM / 泛技术受众）× 7 个维度（已知什么、需要什么、术语、代码、图示、案例来源、深度）。

同一项技术，欠初学者、架构师、CTO 的是三份不同的文档——这个 skill 强制你先定受众，再动笔。

### 4. 输出语言策略

跟随请求语言；不翻译用户的专有术语；当受众语言与请求语言不一致时（如中文请求写英文会议演讲），在开头用一行说明选择再继续。

## 二、具体如何使用

### 安装

Skill 靠目录被发现。二选一：

```bash
# 用户级：所有项目可用（推荐）
cp -R technical-evangelist ~/.workbuddy/skills/

# 项目级：仅当前仓库共享
cp -R technical-evangelist <repo>/.workbuddy/skills/
```

或用 `dist/technical-evangelist.zip` 分发给他人，解压到上述任一路径即可。

### 触发

**不需要显式调用**。模型读 `description` 判断是否命中。以下说法都会触发：

> 技术文章 / 技术博客 / 公众号 / 写篇科普<br>
> 技术分享 / 演讲 / 议题 / PPT / 幻灯片<br>
> 教程 / 上手文档 / 开发者指南<br>
> 技术选型 / 对比一下 A 和 B / 该用哪个<br>
> 技术评审 / 帮我看看这篇写得怎么样<br>
> 想写点什么 / 有什么好选题

### 用法示例

**① 写文章**

```
帮我写一篇技术文章，讲清楚 Agent 的上下文管理。
读者是写过两年后端、但没做过 AI 的工程师。
要有能跑的代码示例。
```

产出：`Audience / Thesis / Format` 抬头 → 可发布全文 → 3 个候选标题。

**② 设计演讲**

```
下个月要给 30 人的内部分享做一场 30 分钟的演讲，主题是我们把构建时间从 12 分钟压到 90 秒这件事。
听众是组里的开发，很多人不关心 CI 原理。
```

产出：演讲定位 → 核心论点 → 故事线 → 分段时长表（含 Demo 时长与降级方案）→ 逐页 slides 结构 → 预期提问及一句话答案。

**③ 技术选型**

```
我们在选消息队列，候选是 Kafka 和 Pulsar。
约束：团队 5 个人，已有 Kafka 运维经验，日均消息量 200 万，未来可能上多租户。
```

产出：决策框定 → 相关维度（会剪掉不相关的）→ 带出处的证据表 → 分场景结论（含"什么情况下两个都不合适"）→ 迁移与退出成本。

**④ 评审别人的稿子**

```
帮我评审一下这篇技术文章，重点看有没有把推测当事实写。
<粘贴文章>
```

产出：6 维打分 → 按影响排序的问题清单 → 原文/问题/改法对照 → 写得好的 2–3 点。

**⑤ 只要选题**

```
我在做 AI 编程工具，想找几个能讲的技术选题，面向已经在用 Copilot 的开发者。
```

产出：选题 × 受众 × 痛点 × 核心洞察 × 差异化角度 × 建议形态。

### 使用要点

- **受众说得越具体，产出越好。**"工程师"的产出远不如"写过 ORM、没写过的后端工程师"。
- **主动给约束**（版本、平台、篇幅、交付时间）。缺了它会自己假设，并在抬头里写出来。
- **要长文时它会给抬头块。**如果抬头里的论点或受众不对，当场纠正，别等它写完两千字。
- **要评审就贴原文**，它不会替你重写全文——它要让你看见"哪里错了"，而不只是拿到改好的版本。
- **别让它编数据。**有基准数据就提供；没有它会标 `[UNVERIFIED]`，不会瞎编。

## 三、工作流

内部执行，不念给你听（除非你要方案）：

```
解析请求 → 归类形态 → 搭建技术模型（问题/背景/机制/架构/用法/权衡/边界）
→ 提炼一句话论点 → 选择叙事结构 → 按格式契约成稿 → 过质量门
```

第 4 步的产出就是抬头块里的 `Thesis`。**这一步过不去，就是选题没想清楚，不该动笔。**

```
│   ├── format-article.md               文章手册
│   ├── format-talk-and-slides.md       演讲与幻灯片手册
│   ├── format-tutorial.md              教程手册
│   ├── format-comparison.md            技术对比手册
│   └── format-social.md                社交与 Release Notes 手册
├── assets/                           可直接套用的模板
│   ├── brief-template.md               内容简报（动笔前的思考工具）
│   ├── article-outline-template.md     文章大纲
│   ├── talk-outline-template.md        演讲 / Deck 大纲
│   └── review-checklist.md             评审清单
└── dist/technical-evangelist.zip     分发包
```

**为什么拆这么多文件？** `SKILL.md` 只有一个任务：**判断该读哪个文件**。

写一篇博客不需要加载演讲时长表和异议处理表。强行全量常驻会挤占上下文预算，反而降低产出质量。原版把全部内容塞进单个 768 行的文件，是这次重构要解决的主要问题。

## 五、质量门

每次交付前自查：

| 维度 | 通过标准 |
|---|---|
| 准确性 | 论断已打标；无编造的细节、基准、版本行为；假设已声明 |
| 逻辑 | 因果链完整；每一节都服务于论点；无无依据跳跃 |
| 受众契合 | 深度、用词、案例匹配声明受众；术语凭实力出现 |
| 记忆度 | 论点只说一次、清晰、可一句话引用 |
| 工程价值 | 读者知道**何时用**，也知道**何时不要用**；权衡已点明；下一步可执行 |
| 语体 | 无 AI 填充、无营销话术、无空开头、无套话结尾、无伪造紧迫感 |

带证据才可使用的表述：*彻底解决 · 行业标准 · 大家都在用 · ……的未来 · 快 10 倍 · 革命性 · 完美方案 · 颠覆式 · 无缝*。

## 六、扩展

**加一种产出形态**：在 `references/` 新建 `format-xxx.md`，然后在 `SKILL.md` 的 Reference routing 表加一行。不要往 `SKILL.md` 正文里塞内容——它就是设计成不长的。

**改评分标准**：只改 `references/quality-rubric.md` 的锚点描述即可，`SKILL.md` 不需要动。

**调受众分类**：改 `references/audience-calibration.md` 的表格行。

**原则**：`SKILL.md` 保持精简，深度内容一律下沉到 `references/`。
