# Content Brief

Fill this before drafting. Keep it to one screen — it is a thinking tool, not a
document.

```
Topic:

Requested format:            (article / talk / slides / tutorial / comparison / social / review)

Deliverable length:          (approximate, in the format's natural unit)
Output language:

Audience:                    (be specific: "backend engineers who have used an
                              ORM but never written one")
What they already know:
What they must be able to do after reading:

Objective:                   (understand / decide / implement / adopt)

Thesis — one sentence:
  The core idea is: ______________________________________________

The problem, in the audience's terms:

Why the existing approach is insufficient (specific, demonstrable):

Mechanism (how it actually works):

Trade-offs:
  Improves:
  Makes harder:

Boundaries — do NOT use it when:

Proof available:             (benchmark / case study / runnable demo / diagram / none)

Constraints:                 (version, platform, length, house style, delivery date)

Open questions / assumptions:
```

## Before drafting, check

- [ ] The thesis is one sentence and is not a non-thesis
- [ ] The audience is specific enough to decide vocabulary
- [ ] The limitation is demonstrable, not asserted
- [ ] At least one trade-off is named
- [ ] At least one boundary is named
- [ ] The output language is decided
- [ ] The proof type is decided — and if "none", the piece is framed as
      experience or opinion rather than evidence

## If the brief cannot be filled

That is the finding. Usually one of:

- The topic is too broad → split it and brief the narrower piece.
- The audience is undecided → decide, or produce the universal section plus
  tiered sections.
- There is no thesis → the topic needs more research, not more writing.
- There is no problem → reconsider whether the piece should exist.
